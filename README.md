# SecureMsg C++ Client

A terminal UI (TUI) secure messaging client implementing the Signal Protocol with post-quantum resistance, zero-knowledge authentication, and blockchain-backed integrity.

## Core Features

- **PQXDH Session Establishment** — Hybrid key agreement combining **X25519** and **ML-KEM-1024** (FIPS 203). Protects against harvest-now-decrypt-later attacks by requiring both classical and post-quantum primitives to be broken.
- **Double Ratchet Messaging** — Provides per-message forward secrecy (symmetric ratchet) and break-in recovery (DH ratchet). All message headers are encrypted to prevent traffic analysis by the server.
- **Group Messaging** — Implements the **Signal Sender Key** protocol, allowing efficient O(1) group encryption.
- **Zero-Knowledge Authentication** — Uses **SRP-6a** (Secure Remote Password) so the server never handles user passwords. Supports **TOTP 2FA** on every login.
- **Local Key Protection** — Long-term identity and session keys are stored locally using **SQLite**, encrypted at rest with **AES-256-GCM** via a key derived from the user's password (**PBKDF2-HMAC-SHA256**, 600k iterations).
- **Tamper-Evident Integrity** — Every 5 sent messages the client auto-exports a signed segment bundle (`direct-X-Y-seg-N.json`), computes a `keccak256` hash, and submits it on-chain to Ethereum Sepolia via a `recordDigest` contract call. A manual **Export Segment** and **Verify Integrity** button are available in the chat panel for direct conversations.
- **Modern Terminal User Interface (FTXUI)** — A high-performance, interactive TUI built with **FTXUI**. It provides a desktop-like experience in the terminal with support for mouse interaction, complex layouts (flexbox-style), and animated transitions.
- **TOTP 2FA with QR Codes** — Multi-factor authentication is required on every login. The client uses `libqrencode` to render QR codes directly in the terminal using UTF-8 block characters, allowing for seamless setup with standard authenticator apps (Google Authenticator, Raivo, etc.).

## Cryptographic Architecture

The project implements a multi-layered key hierarchy to ensure that the compromise of a single message key does not affect past or future communications.

### 1. Initial Handshake: PQXDH
Before messaging begins, a **Post-Quantum Extended Diffie-Hellman (PQXDH)** exchange is performed. This combines four classical Elliptic Curve Diffie-Hellman (X25519) operations with a post-quantum Key Encapsulation Mechanism (ML-KEM-1024).

- **DH1/DH2/DH3/DH4**: Mutual authentication and forward secrecy using X25519. DH4 specifically incorporates the recipient's One-Time Prekey (OPK) for maximum forward secrecy.
- **ML-KEM**: Provides quantum-resistance against "Harvest Now, Decrypt Later" attacks.
- **Binder**: A fixed prefix ensures PQXDH keys are never compatible with classical X3DH keys.

### 2. Message Exchange: Double Ratchet
Once a session is established, the **Double Ratchet** algorithm ensures that every message uses a unique key.
- **DH Ratchet**: Every turn in the conversation triggers a new X25519 exchange, providing "break-in recovery."
- **Symmetric Ratchet**: Derived from the DH Ratchet, it produces a constant stream of unique Message Keys.
- **Header Encryption**: Message metadata (index, previous chain length) is encrypted with a separate Header Key.

### 3. Key Hierarchy

| Key Level                  | Lifetime   | Purpose                                                               |
|:---------------------------|:-----------|:----------------------------------------------------------------------|
| **Identity Key (IK)**      | Years      | Permanent Ed25519/X25519 key used to sign prekeys.                    |
| **Signed Prekey (SPK)**    | Week       | Medium-term key used to establish sessions.                           |
| **PQ Prekey (PQPK)**       | Week       | Post-quantum ML-KEM-1024 key used for session initiation.             |
| **One-Time Prekeys (OPK)** | Single Use | Ephemeral X25519 keys for maximum forward secrecy.                    |
| **Ephemeral Key (EK)**     | Single Use | Temporary key generated by the sender for the PQXDH handshake.        |
| **Root Key (RK)**          | Session    | The "master secret" of the Double Ratchet.                            |
| **Chain Key (CK)**         | Message    | Symmetric ratchet used to generate Message Keys (Group/Direct).       |
| **Header Key (HK)**        | Epoch      | Used to encrypt Double Ratchet headers (metadata privacy).            |
| **Message Key (MK)**       | One Msg    | Used for AES-256-GCM encryption of a single message.                  |
| **Sender Key (SK)**        | Grp Epoch  | Root secret for a member's group chain; rotated on membership change. |
| **Storage Key**            | Login      | Derived from password (PBKDF2) to encrypt local database.             |


### 4. Quantum Resistance & Bit-Security

| Primitive          | Algorithm   | Classical Strength | Quantum Strength  |
|:-------------------|:------------|:-------------------|:------------------|
| Symmetric          | AES-256-GCM | 256-bit            | 128-bit (Grover)  |
| KEM                | ML-KEM-1024 | 256-bit            | 256-bit (Lattice) |
| Signatures         | Ed25519     | 128-bit            | Broken (Shor)     |
| Exchange           | X25519      | 128-bit            | Broken (Shor)     |
| **Hybrid Session** | **PQXDH**   | **128-bit**        | **128-bit**       |

### 5. Cryptographic Implementation (OpenSSL 3.x)

The core cryptographic operations are powered by **OpenSSL 3.x**, utilizing the **EVP (Envelope)** API for maximum security and performance.

- **Provider Architecture**: The client is designed for OpenSSL 3.x providers, allowing it to leverage hardware acceleration (AES-NI) and future FIPS-validated modules without code changes.
- **EVP Interface**: All operations (AES-GCM, X25519, Ed25519, HKDF) use the `EVP_PKEY` and `EVP_CIPHER` abstractions. This ensures that sensitive keys are handled within the OpenSSL secure context and never exposed as raw bytes in the application layer unless necessary.
- **Memory Security**: We utilize `OPENSSL_cleanse` to zero-out sensitive buffers (IKM, shared secrets, plaintexts) immediately after use, mitigating the risk of memory harvesting.
- **Post-Quantum Integration**: ML-KEM-1024 is implemented via the OpenSSL provider interface, ensuring that post-quantum keys are managed with the same rigorous standards as classical primitives.

## System Architecture

The client is a standalone C++ application that integrates several modern technologies:

1.  **UI Layer (FTXUI):** Uses a functional, component-based approach to UI design. The screen is rendered as a tree of elements (Rows, Columns, Windows, Input boxes) that react to user events and state changes.
2.  **Auth Layer:** mutual authentication via SRP-6a + TOTP.
3.  **Keys:** Automated generation and publication of PQXDH prekey bundles.
4.  **Messaging:** End-to-end encrypted payloads using AES-256-GCM.
5.  **Audit:** Auto-export every 5 sent messages → `keccak256` hash → `recordDigest` transaction on Ethereum Sepolia. Requires `eth_config.json` (see below). Group integrity verification is not yet supported.

## Blockchain Configuration

To enable on-chain recording, create `eth_config.json` in the working directory before launching the client:

```json
{
    "private_key": "0x<your-32-byte-hex-private-key>",
    "contract_address": "0x<your-deployed-contract-address>",
    "rpc_url": "https://ethereum-sepolia-rpc.publicnode.com"
}
```

The client loads this file on login. Without it, segment files are still exported locally but the Sepolia transaction is skipped and the status bar will show `(add eth_config.json to record on chain)`.

## Getting Started
